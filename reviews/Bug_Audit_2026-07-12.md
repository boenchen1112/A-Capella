# Bug Audit — Phases 0–6 Codebase (for Sonnet to fix)

> Full audit of `src/`, `tools/`, and `tests/` as of commit `a41936e`, with deep focus on video synthesis/compositing/export as requested. Bugs are ordered by severity within each section. Each entry has: location, what's wrong, why it matters, and the suggested fix. Do not fix anything not listed without flagging it first. Verified-correct areas are listed at the end so effort isn't wasted re-checking them.

## CRITICAL — export/compositing correctness

### C1. Exported video has red/blue channels swapped (BGRA piped as RGBA)
**Files:** `src/Acapella.Engine/Composite/Compositor.cs:15`, `src/Acapella.Engine/Export/ExportEngine.cs:107-114, 132`

`Compositor.Composite` creates the output bitmap with `new SKBitmap(canvasWidth, canvasHeight)` — no color type, so SkiaSharp uses `SKImageInfo.PlatformColorType`, which is **Bgra8888 on Windows**. `ExportEngine.WriteBitmapPixels` then dumps those raw bytes into an ffmpeg stdin declared as `-pix_fmt rgba` (`StartEncodeProcess`). Every exported frame has R and B swapped (skin looks blue, red shirts look blue, etc.).

The decoded input frames (`VideoFrameStreamSource`) are explicitly Rgba8888, but that doesn't matter: `canvas.DrawBitmap` converts correctly *into* the BGRA canvas; the corruption happens at the raw byte dump.

**Why tests missed it:** `CompositorTests` uses `SKBitmap.GetPixel`, which is color-type-aware, and `ExportEngineTests` only ffprobes stream metadata, never pixel colors.

**Fix:** create the composite bitmap explicitly as `new SKBitmap(new SKImageInfo(canvasWidth, canvasHeight, SKColorType.Rgba8888, SKAlphaType.Unpremul))` (preferred, single change), or change the encode arg to `-pix_fmt bgra`. Then add a regression test that exports a solid-red fixture clip and ffmpeg-decodes one output frame to raw bytes, asserting the red channel (not GetPixel) is dominant.

### C2. Per-layer sync offsets are never applied anywhere in mix, preview, or export
**Files:** `src/Acapella.Engine/Export/ExportEngine.cs:29-50` (audio), `:60-76` (video), `src/Acapella.Engine/Mix/MixEngine.cs:32-55`, `src/Acapella.App/MainWindow.xaml.cs:217-224`

`LayerModel.CalibratedOffsetMs` and `ManualOffsetMs` are set by the UI slider, persisted, and round-trip-tested — but **no code path ever consumes them**. Grep confirms the only usages are the persistence DTO mapping, the slider, and the model itself. Consequences:

- Audio mixdown (`ExportEngine.Export`, `MainWindow.PreviewMixButton_Click`) starts every layer at t=0 regardless of offset. The manual fine-tune slider (a Phase 1 acceptance feature) is a no-op.
- Video (`VideoFrameStreamSource`) also starts every layer at t=0, so even after fixing audio offsets, video would desync from its own layer's shifted audio.
- `CalibratedOffsetMs` is never even *written* to a layer at record time (`RecordLayerButton_Click` looks the offset up, prints it in the status text, and drops it).

**Fix:**
1. At record time, store the looked-up calibration on the new layer (`layer.CalibratedOffsetMs = offsetMs ?? 0`).
2. Define total shift per layer: `shiftMs = -(CalibratedOffsetMs) + ManualOffsetMs` (calibration removes recording latency, i.e. trims the head; manual is a signed user nudge — document the sign convention in one place).
3. Audio: in mixdown/preview, pad the decoded float[] with `shiftMs` of leading silence (positive) or skip `shiftMs` of samples (negative) before wrapping in `ArraySampleProvider`.
4. Video: apply the same shift to `VideoFrameStreamSource` — simplest is an ffmpeg `-ss <seconds>` input option for negative shift, and holding the first frame for `round(shift*fps)` frames for positive shift.
5. Duration bookkeeping (`maxSamples`) must use the *shifted* lengths.

### C3. Guide track is never played during recording — the app's core mechanic is unwired
**Files:** `src/Acapella.App/MainWindow.xaml.cs:142-157`, `src/Acapella.Engine/GuideTrack/GuideTrackPlayer.cs` (unused by the app)

When recording layer 2+, the app sets a status message ("Recording layer N with guide track...") but **never plays anything**. The comment at MainWindow.xaml.cs:147-150 says guide playback would be wired "in later phases" once the mix engine exists — the mix engine has existed since Phase 3 and it was never wired. `GuideTrackPlayer` is referenced only by `tools/HardwareChecks`.

Phase 1's `[auto]` criterion "layers 2–4 record with the guide track audible, sample-aligned within ±20ms" passed against `GuideTrackPlayer` in isolation (HardwareChecks Check 4), not against the app's record path, which doesn't have one. The performer currently records layer 2 in silence.

**Fix:** in `RecordLayerButton_Click`, when `nextLayerId > 0`: build the prior layers' mix via `MixEngine.BuildMix` (decode via `AudioDecoder`), play it through the selected output device for the duration of the capture, stop it in `StopRecordButton_Click`. Run the decode/build off the UI thread. See C4 before choosing how to apply the latency offset here.

### C4. `GuideTrackPlayer.PlayDelayed` compensates latency in the wrong direction
**File:** `src/Acapella.Engine/GuideTrack/GuideTrackPlayer.cs:16-28`

The design delays guide *playback start* by the calibrated offset. Work through the timeline: capture starts at T0; guide starts at T0+d and reaches the performer's ears at T0+d+Lo (output latency); their performance of guide-beat-n lands in the capture file at `d + Lo + Li + n` (input latency). Alignment error against the guide timeline is `d + roundtrip` — **the added delay d makes misalignment worse, and nothing ever removes the roundtrip either** (no code trims recorded layers).

**Fix:** start the guide with **zero** added delay, and after capture stops, treat the calibrated roundtrip as the layer's `CalibratedOffsetMs` so C2's fix trims it from the head of the recorded layer at mix/composite time. Delete or repurpose `PlayDelayed`'s sleep parameter. (HardwareChecks Check 4 then needs rewording — it currently validates the accuracy of a mechanism the app shouldn't use.)

### C5. Rubber Band start delay makes pitch-corrected layers arrive late
**File:** `src/Acapella.Engine/Pitch/AutoPitchCorrector.cs:49-95`

`ApplyPitchShift` runs the stretcher in `ProcessRealTime` mode and keeps **all** retrieved output. Real-time mode prepends a start delay (`RubberBandStretcher.GetStartDelay()`, typically ~2048–8192 samples = **46–186ms at 44.1kHz**, larger with `PitchHighConsistency`). Any layer with `PitchBackend = Automatic2B` is therefore shifted late by that amount relative to uncorrected layers, in both preview and export — well outside the ±20ms sync tolerance. Output length also ≠ input length, so the corrected layer's tail is silently truncated (export buffer is sized from *raw* decoded lengths) or falls short.

**Fix:** after the process loop, drop the first `GetStartDelay()` samples from `output`, then pad-with-zeros/trim to exactly `samples.Length` so corrected audio is time- and length-aligned with the raw layer. Add a test: correct a click positioned at a known sample index and assert the corrected click is within a few ms of the same index.

## HIGH — sync measurement & capture

### H1. Latency calibration bakes wall-clock sleep jitter into the measured offset
**File:** `src/Acapella.Engine/Sync/LatencyCalibrator.cs:51-73`

The measured click position is corrected by subtracting a hard-coded 200.0ms because `Thread.Sleep(200)` separates `StartRecording()` from `Play()`. But the capture stream's t=0 is when WASAPI actually delivers its first buffer, not when `StartRecording()` returns — device activation delay plus `Sleep` inaccuracy (±15ms typical timer resolution, worse under load) lands directly in the "calibrated" offset. This can silently eat the entire ±20ms budget.

**Fix (minimal, no new hardware assumptions):** timestamp the *actual* relationship instead of assuming it: record `Stopwatch` timestamps at the first `DataAvailable` callback (t_captureStart) and immediately before `output.Play()` (t_play), and subtract `(t_play - t_captureStart)` instead of the constant 200.0. Remains imperfect (WASAPI buffering) but removes the two largest error terms. Run HardwareChecks Check 1 to confirm run-to-run consistency tightens.

### H2. `PcmConverter.BytesToFloatSamples` silently returns zeros for unsupported formats
**File:** `src/Acapella.Engine/Sync/PcmConverter.cs:7-24`

Only float32 and int16 are handled. A capture device delivering 24-bit or 32-bit int PCM (common for "Stereo Mix"/USB interfaces) produces an all-zero buffer with no error, and calibration then "succeeds" with a garbage offset (cross-correlation of silence picks lag 0 arbitrarily). **Fix:** implement 24-bit (3-byte LE) and 32-bit int conversions, and `throw new NotSupportedException(format.ToString())` for anything else rather than returning zeros.

### H3. dshow audio device selected by WASAPI friendly name
**File:** `src/Acapella.App/MainWindow.xaml.cs:136, 157`

`RecordLayerButton_Click` passes the **WASAPI** capture device's `FriendlyName` into `FfmpegCaptureSession` as the **dshow** audio device name. The two namespaces often differ ("Microphone (Realtek(R) Audio)" vs "Microphone (Realtek High Definition Audio)"); when they do, ffmpeg errors with "Could not find audio only device" and the layer records nothing. `DeviceCatalog.GetDshowDevices()` already parses dshow *audio* devices; the UI just filters them out (`MainWindow.xaml.cs:59`). **Fix:** add a dshow-audio combo (or map selection to the dshow list) and pass a name that ffmpeg actually listed.

### H4. Real-hardware capture likely drops frames: no `-rtbufsize`, default x264 settings
**File:** `src/Acapella.Engine/Capture/FfmpegCaptureSession.cs:39-44`

The dshow capture command has no real-time buffer (`-rtbufsize`) and encodes with libx264 defaults (preset medium), which frequently can't keep up with a live 720p+ webcam feed; ffmpeg then logs "real-time buffer too full ... frame dropped" and A/V drift accumulates — exactly the failure the session notes worried about, and stderr is being discarded so it would be invisible. **Fix:** add `-rtbufsize 256M` before `-i`, and `-c:v libx264 -preset ultrafast -crf 23 -c:a aac` (or `-c:v mjpeg -q:v 5` if CPU-bound) as output options. Keep `.mkv`. Also stop discarding stderr blindly: have `DrainStderrInBackground` optionally retain the last ~50 lines so `Stop()` can surface "frame dropped"/"buffer full" warnings.

### H5. `AvSyncAnalyzer.GetVideoFlashSeconds` assumes the caller knows the frame rate
**File:** `src/Acapella.Engine/Sync/AvSyncAnalyzer.cs:46-81`

Frame index is divided by a caller-supplied `frameRate` (default 30.0) while ffmpeg decodes at the stream's *native* rate. Real captures are 29.97/15/variable fps, so the computed flash time is wrong by the rate mismatch — this is the tool meant to verify within-layer A/V sync on real hardware, so it must not have a hidden 30fps assumption. **Fix:** add `fps=<frameRate>` to the `-vf` chain (mirroring `VideoFrameStreamSource`) so the division is correct by construction, or ffprobe the actual rate.

## MEDIUM

### M1. Aspect ratio is distorted in every rendered cell
**Files:** `src/Acapella.Engine/Export/LayerFrameSource.cs:44`, `src/Acapella.Engine/Composite/VideoFrameDecoder.cs:24`

`scale={width}:{height}` stretches the source to the cell (16:9 webcam into a 4:3-ish cell = visibly squashed faces). This is the first thing the `[human]` export check-in will flag. **Fix:** `scale={w}:{h}:force_original_aspect_ratio=decrease,pad={w}:{h}:(ow-iw)/2:(oh-ih)/2:black` in both decode paths.

### M2. No headroom management: 2+ layers can clip the export
**Files:** `src/Acapella.Engine/Mix/MixEngine.cs:22-29`, `src/Acapella.Engine/Export/ExportEngine.cs:43-53`

`MixingSampleProvider` sums layers; four vocal layers near full scale exceed ±1.0. The float WAV holds >1.0 but the AAC encode hard-clips. **Fix (minimal):** apply a fixed `1/sqrt(layerCount)` scale or a simple peak-normalize pass on `mixedSamples` before `WavFileWriter` (and the same gain in preview via one `VolumeSampleProvider` on the mixer). No limiter needed for v1.

### M3. Changing a parameter does not update a *running* preview
**Files:** `src/Acapella.App/MainWindow.xaml.cs:241-263, 265-305`, `src/Acapella.Engine/Mix/ThreeBandEqSampleProvider.cs:29` (dead code)

The mix graph is built once per Preview click; slider changes mutate `LayerMixParameters` but nothing re-reads them (gain/pan are captured as constants in `BuildLayerChain`, `UpdateGains` is never called). Phase 3's `[auto]` criterion passed by rebuilding the graph in a test, which satisfies the letter of the criterion, but in the app the user must stop/restart preview to hear a change. **Fix (cheapest honest version):** on `MixParam_ValueChanged`, if `_previewOutput` is playing, rebuild the mix and swap it (restart playback at current settings), or hold references to each layer's `VolumeSampleProvider`/`PanningSampleProvider`/EQ and push updates live. Either way, delete or use `UpdateGains`.

### M4. Metronome is audible whenever toggled, not only during recording
**File:** `src/Acapella.App/MainWindow.xaml.cs:100-113`

Locked scope says metronome is "audible only during recording". Currently it plays from toggle-on until app exit (the `WasapiOut` also keeps running silence forever once toggled off). **Fix:** gate `_metronome.Enabled` on an active capture (enable in `RecordLayerButton_Click` if the toggle is checked, disable in `StopRecordButton_Click`), and stop/dispose `_metronomeOutput` when disabled.

### M5. Preview playback never finishes
**Files:** `src/Acapella.Engine/Mix/ArraySampleProvider.cs:19-36`, `src/Acapella.App/MainWindow.xaml.cs:265-305`

`ArraySampleProvider.Read` always returns `count` (silence past the end), so the mixer stream is infinite: preview "plays" forever and the button stays in Stop mode with no auto-reset. Export is unaffected (bounded loop). **Fix:** return actual samples remaining (0 at end) — `MixingSampleProvider` drops ended inputs; then handle `WasapiOut.PlaybackStopped` to reset the button. Note: fixing this makes `Read` return 0; re-check the export read-loop still terminates correctly (it breaks on n==0 — fine).

### M6. Recording failures create zombie layers
**File:** `src/Acapella.App/MainWindow.xaml.cs:157-160`

The layer is added to `_layers` immediately after `Start()`, with no check that ffmpeg started or that the output file exists/has size after `Stop()`. A failed capture (e.g. H3's name mismatch) leaves a layer whose `SourcePath` is missing or empty, which later makes export throw or produce a silent/black cell. **Fix:** on `StopRecordButton_Click`, verify the file exists and has nonzero media duration (quick ffprobe); if not, remove the layer and surface the retained stderr tail (H4) in the status text.

### M7. Export mutates shared state on a background task with no guard
**File:** `src/Acapella.App/MainWindow.xaml.cs:391-421`

`Task.Run(() => Export(_layers, ...))` reads `_layers`/`MixParameters` while the UI can still add layers or move sliders mid-export (only the Export button is disabled). **Fix:** snapshot the project (reuse `ProjectPersistenceService.ToDto`/`FromDto` for a deep copy) and export the snapshot, or disable the editing controls during export.
